## Architecture Pattern

Feature-layer architecture with pragmatic Clean Architecture inside features when behavior justifies it:

```text
feature/
  domain/         pure models and repository contracts        (add when real behavior arrives)
  data/           implementations, DTOs, mappers              (add when real behavior arrives)
  presentation/
    model/        UI models + derived helpers (extension funcs, label/formatters)
    sample/       hardcoded sample data (`*SampleEntries`, `*SampleStats`, `*SampleFavorites`)
    state/        plain-class state holders + `remember*` factory
    components/   feature-scoped composables (cards, sheets, sections, chips)
    util/         pure helpers (validators, math, encoders)
    {Feature}Screen.kt   = Screen (wires holder) + Content (stateless)
```

Add `domain/` and `data/` only when real AniList/session/storage behavior appears. Do not pre-create empty layers or `placeholder.txt` files.

### Feature-group exceptions: `discover/`, `mediaList/` and `mediaDetail/`

`mediaList/` and `mediaDetail/` already render UI (`AnimeListScreen`, `MangaListScreen`, `MediaEntryEditorSheet`, `MediaDetailScreen`, `CharacterDetailScreen`, `StaffDetailScreen`, `StudioDetailScreen`); `settings/` renders its full screen. The groups below are domain + repository + state holders; remaining screens land later without restructuring.

`discover/` is a feature-group with sub-scopes (`dashboard/`, `explore/`, `genre/` and `catalog/`) sharing one `domain/` and one `repository/`:
```text
discover/
  domain/               shared repo contracts (DashboardRepository, ExploreRepository) + model/ (`MediaCatalogFilter`, `DashboardSectionKind.catalogFilter` + shared windows)
  repository/           one impl per scope (dashboard and explore own their queries; genre and the "View all" catalog reuse ExploreRepository's grid query)
  ui/
    dashboard/state/    DashboardStateHolder
    explore/state/      ExploreStateHolder
    explore/ExploreScreen.kt  the DISCOVER search results surface (submitted-query only)
    catalog/state/      CatalogGridStateHolder (one shared grid: a genre is `type + genre_in`; a Dashboard "View all" is its rail's `MediaCatalogFilter`)
    catalog/CatalogDetailScreen.kt  "View all" of a Dashboard rail (title + sort in the toolbar, no Anime/Manga switch; a SEASONAL/UPCOMING_SEASON rail adds a 4-season chip row as the grid's header and the toolbar title follows the selected chip)
    genre/GenreDetailScreen.kt      the genre page (same grid + an Anime/Manga switch header)
```

Dashboard, Explore, Genre and Catalog never import each other directly — only via `domain/`. This is a one-off exception for this group of scopes (genuinely coupled: two angles of the same catalog, plus a catalog filtered by name or by a rail). Every other feature in the app stays flat, with no sub-scopes.

`mediaList/` is the second feature-group, same pattern, for the user's anime/manga lists (`anime/` and `manga/` sub-scopes):

```text
mediaList/
  domain/
    anime/              AnimeListRepository + model/ (entry, section, `completedSection()`)
    manga/              MangaListRepository + model/ (entry, section, `isVolumeBased()`)
    common/             shared list machinery (`SortableMediaListEntry`, `matchesMediaListFilters`, `sectionEntries`/`sectionCount`, sorting)
  repository/
    anime/              `toAnimeListEntry` mapper, AnimeListRepositoryImpl (thin wrapper)
    manga/              `toMangaListEntry` mapper, MangaListRepositoryImpl (thin wrapper)
    MediaListCollectionFetcher.kt  one `MediaListCollection` query (`$type: MediaType`) + fetch, shared by both impls
  ui/
    common/MediaListScreenScaffold.kt  the one list screen (states, search, scroll, filter + sort sheets)
    common/state/       MediaListLoader + ListProgressSaver + MediaListHolder (shared holder contract)
    anime/AnimeListScreen.kt  thin wrapper (sections, empty icon, meta line, format options, entry body)
    manga/MangaListScreen.kt  thin wrapper
    anime/state/        AnimeListStateHolder (implements MediaListHolder)
    manga/state/        MangaListStateHolder (implements MediaListHolder)
```

`anime/` and `manga/` never import each other directly. Genuinely different things stay split: media formats, list sections (anime splits COMPLETED by format, manga doesn't), the entries' progress shape, the progress/airing sort comparators, the meta line, the empty icon and the card body; the collection query, the loader/saver, the rail assembly and the whole screen (`MediaListScreenScaffold`, over the `MediaListHolder` contract) are shared. The format options come from the shared core rule `mediaFormatsForType`, and the filter sheet hides its season group on manga (`MediaListHolder.supportsSeasonFilter`, whose holder also ignores a stored season — AniList has no season for manga); the year filter compares `seasonYear`, which both mappers fill from `startDate.year` when the server leaves it empty.

## State Pattern

- A stateful feature owns a `*StateHolder` (plain Kotlin class) exposing derived read-only views over Compose-backed state (`var x by mutableStateOf(...)`) and intent-style mutations (`load`, `refresh`, filters, edits). Real examples: `ExploreStateHolder`, `AnimeListStateHolder`, `ProfileStateHolder`, `CalendarStateHolder`. Paginated lists delegate to the shared `ui/state/PagedList` (Compose state + append/dedup/cancel rules) instead of hand-rolled lists.
- The holder is constructed with its repository (plus scope/store where needed); several have a pure `create*` factory for tests (`createProfileStateHolder`, `createCalendarStateHolder`, `createNotificationsStateHolder`). `SettingsState` additionally owns a `rememberSettingsState()` Composable factory (its async load/save/error drives the screen); the rest expose Compose state directly.
- The four detail holders (`MediaDetailStateHolder`, `CharacterDetailStateHolder`, `StaffDetailStateHolder`, `StudioDetailStateHolder`) extend `mediaDetail/ui/state/DetailStateHolderBase<D, S>`: the base owns the visible `detail`, the load/refresh switch, the 5-entry `DetailCache` snapshot, the derived `isFavourite` and the optimistic favourite toggle, and a scope only supplies its hooks — `fetchDetail`, `onDetailLoaded`, `cancelPages`/`clearPages`, `snapshot`/`restore`, `isSnapshotValid`, `isFavouriteOf`/`isFavouriteOfSnapshot`, `withFavourite`/`snapshotWithFavourite`, `requestToggleFavourite`, and the optional `onCacheMiss` (studio's default sort). The base also exposes `applyFavourite(id, value)` (mirrors an external change into the visible page and the cached snapshot, no network) and `favouriteFor(id)` (its read twin), driven by the root favourite router (see Profile Layout). Each scope's `PagedList`s stay in its holder; studio also implements `GridSortHolder`.
- The two user-list holders (`AnimeListStateHolder`, `MangaListStateHolder`) extend `mediaList/ui/common/state/MediaListStateHolderBase<T, S>`: the base owns the `MediaListLoader` (TTL + latest-request guard), the optimistic `ListProgressSaver`, the sort/filter state, `load` and the section filtering/counting, and a list only supplies its hooks — `fetchList`, `saveProgress`, `allSection`/`statusOf`, `progressOrder`/`airingOrder` — plus its own `+1` increments (which call the base's protected `enqueue`). The list-screen view settings travel as one `MediaListScreenSettings` value (sheet open flags stay outside).
- **Latest-request wins** goes through `ui/state/LatestRequest` (used by the profile/explore/genre/notifications/settings/media-list/social-list holders and `PagedList`): it stores the new job before cancelling the old (so a body that ignores cancellation cannot write), hands the body an `isCurrent()` to gate writes, and runs its `onSettled` (spinner off) only while it is still the latest. A `cancel()` without a relaunch forgets the job, so its `onSettled` does not run: the canceller turns its own spinner off.
- `SettingsState` is a Compose-backed holder (`settings/ui/state/`) over `SettingsRepository` + `SettingsStore` (hydrate + debounced save, `canSync` gate, `refresh()` deduped per session with `force` retry). `App` creates one per session via `rememberSettingsState()` (keyed by auth flip) and passes it to `Root`, which calls `refresh()` on first open (`LaunchedEffect(state.isOpen(RootOverlay.Settings))`) and forwards it to `SettingsScreen`; guests get `canSync = false` (local-only, never touches the network).
## Dependency Rules

- `feature -> core`: allowed.
- `feature -> ui`: allowed.
- `ui -> core`: allowed.
- `root -> feature`: allowed.
- `feature -> feature`: not allowed.
- `core -> feature`: not allowed.
- `core -> ui`: not allowed (core has zero Compose imports; enforced by grep, see validation).
- `ui -> feature`: not allowed.
- `feature -> root`: not allowed.

Cross-feature coordination belongs in `root` or neutral `core` contracts.

Practical test before placing code: *"If I deleted feature X tomorrow, would this file break?"* If yes, it does not belong in `core/` or `ui/` — it belongs in feature X.

## Layer Map (`core/` vs `ui/`)

`core/` is infrastructure + neutral domain, organized feature-first like `app/`
(each concept owns its layers; no empty layers). No Compose, no UI types
(not even `Color` in models — palette travels as the raw hex `String`,
converted at the UI boundary). Contents:

```text

  network/domain|repository/    transport only: Ktor GraphQL client, NetworkResult, endpoints,
                                rate limiter, HTTP client + `PageInfoDto` (never import DTOs
                                from UI directly, map at feature boundaries)
  platform/domain|repository/   system services: `Connectivity` (image quality), `UrlOpener`,
                                `ShareLauncher`; platform impls (Android/iOS) in `repository/`
  media/domain|repository/      media vocabulary (format/season/type/status/dates/genres/grid item)
                                + `mediaFormatsForType` (the one per-type format rule
                                Explore and the lists share)
                                + AniList media DTOs/mappers (`dto/MediaDto`, `dto/FuzzyDateDto`,
                                titles, cover sizes, grid-item/release-date mappers)
  person/repository/            person DTOs (character/staff/studio) + person cover sizes
                                (AniList placeholder handling)
  medialist/domain|repository/  list-status contracts + `MediaListEntryRepositoryImpl`
                                (save/progress/favourite/delete), list sort vocabulary
                                (`UserListSort`, `MediaSort`) + sort persistence, and the
                                neutral score vocabulary (`ScoreFormat` + parse/format helpers,
                                consumed by settings, root and the profile statistics)
  storage/domain/               settings/filter keys and stores, plus `FileStore` (cache-sized text files)
  language/domain/              string tables only (LanguageStrings, EN/ES, AppLanguage) — no CompositionLocal
  navigation/domain/            routes, AniList deep-link parsing (`parseAniListDestination`),

  model/                        neutral domain vocabulary (CoverSizes, FilterOption, compact count,
                                ImageQuality, Page, calendar dates, notification buckets, page sizes)

  util/                         pure helpers with no feature owner (`DetailCache`, URL parsing/host normalization)
```

`ui/` is the shared Compose UI. Everything visual and reusable lives here, nothing else:

```text
ui/
  components/   shared composables (Toolbar, TabBar, SearchField, MessagePanel, ChipRail, DatePickerField, DetailPosterGrid, …) — no layer prefix, package disambiguates
  icons/        shared toolbar primitives (AppIcons: Search, Back, Clear)
  language/     LanguageProvider (CompositionLocal) + searchHintFor()
  theme/        Theme, AppPalette seeds (Default/Ocean/Sakura/Forest/Amber/Violet/Mono) + AppPaletteStyle (global style)
```

UI is 100% shared Compose Multiplatform in the `shared` module — no native
SwiftUI/UIKit surfaces are planned (`iosApp` is only the entry point: token
storage, OAuth launcher, `onOpenURL`). No extraction of `ui/` into its own
Gradle module: single-dev overhead with no benefit. The boundary stays
package-level, enforced by the dependency rules above.

## Lazy Loading Network Strategy (HTTP 429 Prevention)

State holders do NOT load automatically inside constructor `remember` blocks:
- State holders never load in constructors or `remember` blocks: loads are explicit (`load*()` / `refresh()`), so nothing fires without a user or screen effect behind it.
- `SettingsState.refresh()` fires once per session from `Root` on first settings open (`LaunchedEffect(state.isOpen(RootOverlay.Settings))`); saves debounce 600ms. Guests never load (`canSync = false`).
- The rate limiter is fixed at 28/min (`AniListRateLimiter`): AniList's `X-RateLimit-*` headers do not reflect its degraded serving mode, so the limit is never read from headers. `NetworkThrottle.waitingRequests` (a single `StateFlow<Int>`) counts the requests parked in the wait, and `LoadingPanel` shows a secondary line while it is `> 0` — never on a timer or a merely slow network.

## Root Responsibilities

- `Root` is the app-level orchestrator. It wires the session `SettingsState`, derives the topbar title, and routes the content area.
- `root/state/State.kt` holds: selected tab, selected animation/reading sections, the open overlays as one `Set<RootOverlay>` grouped by `OverlayLayer` (sheets / above the detail / below the detail) read and written through `open`/`close`/`isOpen`, `detailStack` (media/character/staff/studio/genre/catalog push + `isDetailOpen`; `DetailMenu`/`DetailSort` are overlays of the sheet layer), search active/query, and current profile draft. The editor keeps its own fields (it carries data) and counts as an above-detail layer in back order. The progressive back order is sheets → above-detail (modals/settings/editor) → detail → search → Explore results → below-detail overlays → system: the search and its results mode are tab-surface states, so a detail opened from the results closes first, then the field, then the results, then the below-detail overlays. `isSearchVisible` gates the painted search field: while a detail, the editor or an above-detail overlay draws over the tab, the toolbar shows that surface instead (the search itself stays open). Explore results add `exploreResults` (raw session flag, survives a tab change) and `isExploreResultsVisible` (tab-scoped: `selectedTab == DISCOVER`, field closed, no detail) — the getter drives the toolbar, the filter routing and the back branch, so ANIME/MANGA never inherit the results toolbar or its back step; `closeSearch` restores the sent query (an unpublished edit is discarded).
- `root` owns topbar search state for DISCOVER, ANIME and MANGA via `Toolbar` (PROFILE has no search):
  - Normal state: topbar actions.
  - Active search: replaces title with `SearchField`; left icon becomes ChevronLeft; system back closes the field, then the Explore results (both below the detail in back order).
- `root` owns the settings overlay via `State.isOpen(RootOverlay.Settings)` (single source for title, content and back; it opens with `State.open(RootOverlay.Settings)` and closes with `CloseOverlay`). Open means `Toolbar` with back + `settingsTitle` and zero actions; the content area renders `SettingsScreen`.
- `root` owns media detail via `State.detailStack` (single source for title, content and back). Open means a full-screen detail page over the current tab with the tab bar hidden and trailing actions: media → edit / favourite / overflow; character/staff → favourite / overflow, studio → sort / favourite / overflow, genre → sort / overflow, catalog ("View all") → sort only (the shared sort sheet edits the studio/genre/catalog grid holder and the grid re-queries; overflow: open in AniList + share, routed per active destination — a genre's URL is the catalog search filtered by genre, percent-encoded, following the selected Anime/Manga chip). A guest sees only the overflow — plus the sort the studio/genre grids own — never the pencil or the heart (and `ACTION_EDIT`/`ACTION_FAVOURITE` are no-ops without a session, so a stale id can never open the editor with no session or fire a favourite mutation). Refresh, cache invalidation and the favourite action resolve the active destination through the `DetailHolder` contract (`detailHolderFor(...)`), and the detail sort sheet through `GridSortHolder` (`gridSortHolderFor(...)`), instead of a `when` per call site; `load` stays explicit per destination. The toolbar carries the title only for the list-shaped destinations — a "View all" list and the genre page (`detailToolbarTitle`) — while media/character/staff/studio keep theirs in the hero (the bar shows nothing for them). A "View all" list renders the full paginated section; back pops one destination at a time (`BackStep.CloseDetail`) — only the favourites "View all" adds an edit step (`BackStep.CloseFavoritesEdit`) before its own page — and, since the detail renders over calendar/explore/notifications, it closes before them (one back per visible layer).
- Root owns per-surface saved UI state: the content area is wrapped in a `rememberSaveableStateHolder()` keyed by slot tab + view (`tab` / `settings` / `detail:<entryId>` / overlay) with `key(surface)` inside, so each tab, each detail-stack entry (identity per push, `State.detailEntryIds`) and each overlay keeps its own saveable scroll state; a popped entry drops it. The provider lives inside `AnimatedContent`'s content lambda (two slots compose during a tab transition, so equal keys would crash) and the modals (sign-in, editor, share) stay outside it.
- `Toolbar` takes primitives + callbacks (`onNavigation`, `onAction(id)`, search callbacks); `Root` maps action ids (`ACTION_SEARCH`, `ACTION_SETTINGS`, …). Filter/sort actions are currently no-op until their screens land; the calendar action opens the schedule overlay (`State.isOpen(RootOverlay.Calendar)`).

- `profile/` is flat: `domain/` (+`model/`) owns `ProfileRepository`, `ProfileData`, `ProfileStats`, `ProfileFavorites`/`ProfileFavorite` and `ProfileFavoritesCategory` (plus the pure `itemsFor`/`nonEmptyCategories`/`removeFavorite` helpers, `ProfileFavoritesPageSize`), `ProfileFollow`/`ProfileFollowsKind` and `ProfileReview` (+`ProfileListPageSize`); `repository/` owns `ProfileRepositoryImpl`, the mappers, `ProfileCacheDto` and `ProfileDiskCache`; `ui/` owns `ProfileScreen` (+ its header/sections), `stats/ProfileStatisticsScreen`, `follows/ProfileFollowsScreen`, `reviews/ProfileReviewsScreen`, `favorites/ProfileFavoritesGridScreen`, the `ui/model` helpers and the four state holders.

- **Header entries are counters**: the flat header panel's four counters (anime, manga, following, followers) are buttons (≥48dp touch target, `Role.Button`); anime/manga open [[ProfileStatistics]] seeded on that type, following/followers open `ProfileFollows(kindId)`. Under the header sits a single **Reseñas/Reviews** row (`OptionGroup` + `SettingsRow`) opening `ProfileReviews`. The three pages are detail-stack destinations like the favourites grid: title in the toolbar, back closes them, and they carry no trailing actions.
- **Statistics** (`DetailDestination.ProfileStatistics(type)`, `ProfileStatisticsScreen`): 0 extra requests — it reads `ProfileStateHolder.stats`, already on the profile query (disk cache included). A pinned `CatalogChipRail<MediaType>` switches anime/manga (changing it returns to the top); the summary is an `OptionGroup` of rows (count, mean score, days/volumes, episodes/chapters); then score/format/status/genres distributions as shared `ui/components/DistributionPanel`s (a framed flat panel of `DistributionBar`s, its track a `PillShape`). Bar order: score ascending, the rest by count descending. Labels reuse the shared vocabulary (`parseMediaFormat(...).label`, `parseMediaListStatus(...).label(strings, isManga)`, the raw genre). Score display goes through `ui/model/ProfileStatsFormatting`: `meanScore` is always 0-100 on the wire, so it is scaled into the viewer's `core` `ScoreFormat`; `statistics.scores[].score` already arrives in the viewer's format except POINT_100 and POINT_10_DECIMAL, which ship up to 20 buckets on the 0-100 scale and are grouped by tens; POINT_3 reuses the shared smiley representation. `profile` imports only `core` — never `settings`.
- **Following/Followers** (`DetailDestination.ProfileFollows(kindId)`, `ProfileFollowsScreen`) and **Reviews** (`DetailDestination.ProfileReviews`, `ProfileReviewsScreen`): one `Page` query each (`following`/`followers` or `reviews(userId, sort: [ID_DESC])`), paged with `PagedList` + `LatestRequest` + `LoadMoreEffect` like the favourites grid. Each row is the shared `MediaCoverCard`: the user's avatar as its cover / the name as title, or the reviewed media's cover + title with the summary (two lines) and the review's 0-100 score as `titleTrailing`. Tapping a user opens `anilist.co/user/{name}` through `UrlOpener`; tapping a review pushes the reviewed media's detail over the page. Empty states are their own `MessagePanel` texts.
- **Social cache policy**: the follows and reviews lists are **public AniList data, kept in memory only** (never on disk), within the shared 5-minute `AniListNetworkPolicy.CACHE_TTL` — re-opening the same list while fresh costs 0 requests, a cold open one, and each page one more. The header counters keep coming from the profile query (0 extra requests).
- **"View all" page** (`DetailDestination.ProfileFavorites(categoryId)`, a detail-stack page; the category travels as its enum name because core must not import `profile`): the toolbar carries only the title and the edit toggle — a pencil (`AppIcons.Edit`) to enter and a check (`AppIcons.Check`) to leave. In edit mode every poster shows `ProfileFavoriteRemoveButton` over the cover (`DetailPosterGrid.cardOverlay`, its visible 32dp circle 8dp from the corner — the compact button's own air, no extra padding) and every studio row shows it as `SettingsRow.trailing`; tapping does not navigate. Studio rows keep the same 48dp height in both modes: the trailing control is an overlay centered at the row end and does not contribute height. The edit flag is root-owned (`State.favoritesEditing`, `BackStep.CloseFavoritesEdit`): back exits the mode before the page, and closing the page / switching tabs / `reset` drop it.
- **Grid removal** (in `ProfileFavoritesGridStateHolder`): optimistic through a getter filter (`removingIds`/`removedIds` over the untouched `PagedList`), so a rollback on failure reappears at its original index for free; one `FavouriteRepository.toggleFavourite(category.toFavouriteTarget(id))` request per removal, the button disabled in flight, a compact `actionError` on failure, and the root router flips detail hearts. No `canEdit` gate: the grid always comes from the network. On success the grid tells the profile to drop the item from memory and rewrite its cache (`removeFavoriteLocally`, no request) and advances its own `revision`, so neither is marked stale by its own edit.
- **Gap-free paging after removals**: AniList pages by offset, so `k` removals shift the list up by `k`. The holder counts `removalsSinceLoad` and the next `loadMore` re-reads from `currentPage - (k-1)/ProfileFavoritesPageSize` (never below 1; ≤25 removes keep the same page), then advances normally with the existing dedupe (at most one extra request on the next load). Because re-reading can keep the page number unchanged, `LoadMoreEffect` is fed a monotonic `loadKey` bumped on every finished load instead of `currentPage`, so the footer re-arms.
- **Cache**: `ProfileStateHolder.load(userId)` paints the per-user disk cache ([ProfileDiskCache], the whole `ProfileData`) then always revalidates against the network; the in-memory 5-minute TTL means re-opening the profile right after a successful load costs 0 requests, while a cold start costs one. A favourite toggled anywhere (`FavouriteRepository.revision`) makes the loaded profile/grid stale (reload on next open; no extra request by itself). The file is cleared with the lists on logout/401.
- **Favourite changes across surfaces**: `FavouriteRepositoryImpl` bumps a monotonic `revision` after every successful toggle. It (a) stales the profile/grid so their next open reloads, and (b) an explicit `RootHolders.onFavouriteChanged(target, value)` router applies the change to the detail holder of that kind via `DetailStateHolderBase.applyFavourite` (visible page + cached snapshot, no network). The grid's removals and the entry editor both call the router (optimistically, reverted on failure); the editor also seeds its heart from the holder (`favouriteFor`) instead of `loadEditorData` when the holder knows that id.
- Guest on PROFILE = sign-in prompt (the gated-tab `MessagePanel`), like the two lists.
- **Unread dot**: the profile request adds `Viewer { unreadNotificationCount }` as a second root field (0 extra requests); `ProfileData.unreadNotificationCount` carries it from the network only (never in `ProfileCacheDto`, so a stale dot never survives a cold start) and `ProfileStateHolder` forwards each non-null count to the notifications holder, the single owner of the dot. A null (cache) never blanks a live count.
- Cross-feature navigation (e.g. a "See more" rail jumping to a list tab) goes through `Root` callbacks — never feature→feature imports.

## Notifications Layout

- `notifications/` is flat: `domain/` (+`model/`) owns `NotificationsRepository`/`NotificationsPage` and the `AppNotification`/`NotificationKind`/`NotificationTarget`/`NotificationFilter` vocabulary; `repository/` owns the impl, the DTO and the mapper (API type → `NotificationKind`, target URLs built in one place); `ui/` owns `NotificationsScreen`, the `ui/model` presentation helpers and `NotificationsStateHolder`.
- **Exact kind, never a bucket**: `NotificationKind` has one entry per AniList `NotificationType` (its `apiType`) plus `UNKNOWN` (a type we don't model is kept with the generic `otherLabel`, never dropped). There is no stored category. Each kind gets its own phrase from `LanguageStrings` (with the user/media/thread as nullable params and the fallback wording inside the function); `AppNotification` also carries `reason`/`notes`/`status`/`deletedMediaTitles`, which feed the detail sheet (cleaned with the shared `core/util` `stripHtml`, blanks dropped).
- **Filters overlap like Otraku**: `NotificationFilter.kinds()` lists the exact kinds per filter (activity includes messages; replies include the activity ones they came from; media includes the three submission kinds). `toAniListTypes()` maps them to `apiType` with `mapNotNull`, and `UNKNOWN` is never listed. `NotificationBucket`/`apiTypes` (settings) are untouched.
- **Page, not sheet** (`RootOverlay.Notifications`, BELOW_DETAIL): `Root` renders it like the calendar (tab bar hidden), the toolbar carries the title ("Notificaciones") and only back, and a notification pushes its detail **above** the page, so back returns to the feed with its position. Tapping a row without details routes by `NotificationTarget`: media/staff/character → their detail, follow/activity/forum → the web, `None` (a deleted title, a rejected media submission) → nothing. A media data change/merge/deletion or one of the three submission updates opens a page-local `ModalSheet` (the `SettingsScreen` pattern, not a RootOverlay) titled with the notification text: Reason, Notes, Status (submission statuses normalized before translating, unknown values raw) and Affected titles one per line. Its primary "Open" action appears only for Media/Character/Staff targets, closes the sheet and pushes the detail; Web/None have no button. PROFILE's toolbar entry is the bell: a lone circle, `ToolbarAction.badge` while `unreadCount > 0`, session-only; the gear sits beside it as its own circle.
- **Opening is reading**: `onOpen()` always returns to the ALL filter (clearing a leftover filter's list) and resets the global server count — `resetNotificationCount` is global, so it is only ever sent with ALL. `refresh()` (pull/retry) resets only on ALL; a filter's page-1 count is left to the server. The fresh-and-read shortcut (5-minute TTL) skips the request only on ALL.
- Each row is a `MediaCoverCard` (cover + the kind's text, never empty + the timestamp), the same list row as the anime/manga lists, the calendar and the "View all" lists — no person/avatar special-casing. The timestamp is the readable date plus, in parentheses, the past countdown (`timeAgoLabel`, the past mirror of `airingCountdownLabel`: two worded units, singular/plural), down to "(now)"; from 7 days on it is just the date. The phrase is assembled by `LanguageStrings`.
- The unread dot is owned by the notifications holder (fed by the profile), so a cold start shows the last known value and a page open zeroes it. **Unread rows**: on every successful reset load the holder records `highlightCount = max(count before the request, count reported by page 1)` (AniList may answer with either), then zeroes `unreadCount`. Only the ALL filter paints it — the first `highlightCount` rows show an 8dp `primary` dot in `MediaCoverCard.titleTrailing` (contentDescription "Nueva"/"New"); filtered feeds never highlight. Filter loads/refreshes leave the count alone, so switching filters and coming back to ALL keeps it until the next reset load. The card surface itself is unchanged.

## UI Decisions

- Bottom tab labels (4):
  - Spanish: `Descubrir`, `Anime`, `Manga`, `Perfil`.
  - English: `Discover`, `Anime`, `Manga`, `Profile`.
- Home has no banner/avatar and no embedded search row. Search belongs in the topbar.
- **Glass rule (validated sep-2026; tool recipe 5.4):** glass is reserved for floating tools — Toolbar, TabBar, buttons, interactive chips and `TrailingPill`. They take `toolContainerColor()` + `toolBorder()` (resolved from `SurfaceStyle`: translucent glass, or flat `surface` + `outlineVariant`). Content (cards, panels, bands, `OptionGroup`, `SheetTextField`) always uses the flat recipe (`solidContainerColor()` + `flatBorder()`). Buttons go through `ui/components/AppButton`: `Secondary` is the tool recipe, `Primary` (the flow-closing action — Save, Retry, Sign in) is an opaque `primaryContainer` fill with no border. A glass pilot on the session card washed out in light mode (translucency flattened, shadow + 40% border rendered a ghost edge).
- **Glass corruption rule (validated sep-2026):** never chain `.shadow().clip()` on inline content — the offscreen compositing layer seals the container alpha and composites it as an opaque inner square. Inline surfaces take the flat recipe (`solidContainerColor` + `flatBorder`); floating tools carry elevation on their own `Surface`/`Button` (`shadowElevation`), never a chained modifier.
- **Card vs edge-to-edge (validated oct-2026, radii unified 5.4):** on detail pages, a framed card (`MediaDetailPanel`) marks a **data block** — the information grid and the link rows — because grouping tabular content reads better boxed. The panel is **flat**: `surface` fill + `outlineVariant` border (exactly like the list cards), never glass — it groups, it does not float. **Media and prose stay edge-to-edge**: the banner hero, the horizontal rails (characters/staff/related/recommendations), the synopsis, the **stats row** (no frame: three columns with an icon, the value and the label), the **chip rows** (media genres and tags under their header; a person's roles/occupations live inside the hero column as a `FlowRow` of `FlatChip`s) and the **next-episode band**: a single chip group needs no frame, and grouping labels reads worse boxed; the band is a flat full-width rectangle (`surface` + `outlineVariant`, 16dp radius, inert) so it does not read as a button. The **trailer** is a framed 16:9 panel (`surfaceVariant` + `outlineVariant`, 16dp radius, it opens the video). Radii are tokens (`ui/components/Shapes.kt`): `CoverShape` 12 (covers), `PanelShape` 16 (panels, cards, bands, groups, sheet fields), `PillShape` 24 (buttons, toolbar capsules, chips).
- **Chip language**: `ui/components/ChipPill` owns the interactive pill recipe (selected = primary container, rest = tool recipe, ripple on tap). `ui/components/ChipRail` draws the rail and `FlatChip` the **flat, inert** label chips (`surface` + `outlineVariant`, no glass, no click) for labels: tags, roles and occupations; the Anime/Manga selector reuses the rail through `ui/components/CatalogChipRail`. The **studio and genre chips** stay interactive on purpose — they open the studio/genre page (a genre chip is inert only when the media's catalog is unknown, so no page can be opened). `ui/components/TrailingPill` is the compact trailing control (a rail's "View all", the voice-language selector): label with optional leading/trailing glyphs on the same glass/solid recipe. `ui/components/CoverImage` is the one cover box (token size + `CoverShape` + palette/`surfaceVariant` placeholder + optional border and overlay), used by the row card, the poster card and the person/media heroes.
A rail inside a card gets boxed in (first/last cards clip on the rounded corners, the inner padding hides content) and loses the lateral bleed that signals "scroll for more". This applies to all four `mediaDetail/` scopes (media, character, staff, studio), not just media.
- **Card insignias**: cover badges are built in one place, `ui/components/CoverStats` (`scoreBadge` → `85%`, `popularityBadge`/`favouritesBadge` → `compactCount()`), and painted by `CoverStatBadge` (translucent icon+value pill) on the top corners of a poster. The dashboard picks which two a rail shows via `DashboardSectionKind.cardStats()`; the studio grid always shows score + favourites. Global favs use outline `AppIcons.Favorite`, the user's favourited state the filled twin. The anime/manga list rows render a glyph-only pill (no star/number) when the score format is smiley.
- **Poster card**: `ui/components/PosterCard` is the one poster card of the app — token-sized cover + up to two `CoverStatBadge` + two reserved title lines + an optional subtitle, one radius (12dp), inside `CardCappedDensity`, plus an optional `overlay` slot painted last over the cover (e.g. the profile's edit-mode remove button). The type scale steps with the token: a `Rail` card reads `bodySmall`/`labelSmall`, a `Featured` one (a grid cell, the featured rail) `bodyMedium`/`bodySmall`. Rails (`MediaRail`, which forwards a per-item `cardOverlay` and drops navigation when it is set), the "View all" grids (`DetailListScreen`) and the studio/genre grids all draw it, so a poster looks the same everywhere; it takes only primitives (a null `onClick` renders a display-only card). `SettingsRow` takes an optional `trailing` widget instead of the chevron (the profile's edit-mode remove button on a studio row); it is painted as a centered end overlay that reserves 56dp (48dp touch target + 8dp gap) but never adds row height, so a row measures the same with and without the control.
- **Card type scale**: title stays `titleMedium` (weight 500 beats `titleLarge`'s 400); episode/date line is `bodyMedium` + `onSurface`, secondary meta `bodyMedium` + `onSurfaceVariant`. Hierarchy by color, not size.
- **Images**: cover-bearing models carry a `CoverSizes` (medium/large/extraLarge; people images only ship large/medium). **Cover sizes are tokens** in `ui/components/CoverMetrics`: `CoverSize` carries the width **and** its 3:4 height (`Modifier.coverSize(token)`), so no surface can invent a size and a rendered poster always matches its token — `CoverSize.List` (111dp) for row cards (lists, calendar, "View all" rows), `CoverSize.Rail` (131.5dp, the exact midpoint of the other two) for every rail card, and `CoverSize.Featured` (152dp) for the dashboard's featured rail, the media/person heroes and a grid cell. Grids use `GridCells.FixedSize(cell.width)` + `Arrangement.SpaceEvenly` (no horizontal content padding, so the air between columns equals the one at the edges) and size their cells with `ui/components`' `gridCoverSize(availableWidth)`: it starts from the standard token — `Featured` while at least two columns fit with a 12dp gap between and around, otherwise the next token down (`Rail`) — then grows the cell to fill the width, never past `GridMaxGrowth` (+25%). The surplus beyond the cap goes back to even air, so a narrow phone keeps two readable columns and a wide one never leaves a huge margin. The "no invented sizes" rule holds: the cell (and its 3:4 height) always derives from the token. `rememberCoverUrl(cover, size)` picks the image variant from the same token, and `PosterCard`/`MediaCoverCard` cap the OS font scale at 1.3× so cover badges never collide. A person image that is AniList's shared placeholder (`.../anilistcdn/{character,staff}/{large,medium}/default.jpg`, verified against the live API) maps to null in `personCoverSizes`, so a person without an image falls back to the grey placeholder instead of the blue "NO IMAGE" art. A **Settings → General → Image quality** row (`AUTO`/`HIGH`/`LOW`, local-only) drives which variant the shared cover composables resolve via `LocalImageQuality`; `AUTO` follows the connection reactively (unmetered → HIGH, metered → LOW) through `Connectivity` (a `StateFlow` wired in `MichiDependencies`; Android recomputes from the active network on every change (`registerDefaultNetworkCallback`, never trusting the callback's own value; `NOT_METERED`/`TEMPORARILY_NOT_METERED`, unknown counts as unmetered, Data Saver is intentionally not consulted because Android only applies it to already-metered networks) and iOS uses `NWPathMonitor`). One Coil `ImageLoader` (crossfade + memory cache capped at 20% of the app heap) is installed once from `App`; its disk cache is explicitly capped at 64MB in the same folder Coil's default singleton used (`coil3_disk_cache` under the platform temporary directory), so an existing oversized cache is reused and trimmed by the LRU instead of orphaned. Covers resolve per rendered width (`CoverSizes.forWidthPx`, density-aware); the dashboard rails paint the cover's `color` while loading.
- **Session cache**: a cold start with a stored token shows the shell immediately from a cached viewer (`CachedViewerStore` over the store — id/name/avatar/banner + the four settings, no `about`) and refreshes in the background; a 401 clears token + cache → Anonymous, and a network error keeps the cached shell instead of flashing Error.
- **Dashboard cache + preload**: rails are kept **in memory** per media type **and** 18+ gate, within the shared 5-minute `AniListNetworkPolicy.CACHE_TTL` (nothing on disk: a cold start always goes to the network). Loading/refreshing are tracked **per type**, so an Anime request finishing never leaves (or sets) Manga's indicator — the spinner-forever bug after switching to an already-loaded type. `load()` skips the network while the in-memory rail is fresh, and a response whose gate changed mid-flight is discarded. The holder is created with the applied gate (so the screen's first sync never forces) and reads its strings provider **once per request** (a load never mixes languages), so it is not recreated on a language change and the Anime/Manga selection survives. A language change calls `invalidate()` — drops memory and bumps an observable **generation**, launching nothing — and the screen reloads when it is visible again (its effect keys on the generation), so a change made on another tab or under Settings never fires a background request. A gate change also drops memory and reloads **without forcing** (the new gate has no memory yet, so it fetches). The other type is preloaded once after the first successful load (respects the TTL; a select during that preload joins it instead of fetching twice; never surfaces an error).
- **Persistence policy**: on disk live the user's saved lists (one file per user/type in the app cache folder via `FileStore`, not `SettingsStore` — a big list would bloat `SharedPreferences`), the viewer profile (one file per user in the same `FileStore`: the whole `ProfileData` is painted on open and then always revalidated, so the network call is 0 while the 5-minute TTL is fresh and 1 otherwise; removing a favourite rewrites it) and the settings, plus two technical caches — the external-link site catalog and Coil's image cache. The saved lists hydrate a cold start instantly (mapped on read with the current `splitCompleted`) and are **always** revalidated against the network (the file is never fresh: the list is edited from the web and other devices); the revalidation is silent while hydrated entries are shown, and a failed one keeps them with the usual compact retry row. While the entries are only hydrated (not yet confirmed by the network, including after a failed revalidation) the `+1`/completion is disabled — editing from a stale progress value would send absolute progress backwards; the entry editor (pencil) still loads the entry fresh from the server. Discover, detail, calendar and the catalog grids (genre / "View all") keep their data **in memory only**, within the shared 5-minute `AniListNetworkPolicy.CACHE_TTL`, so a cold start always re-reads the network. Logout / 401 / an expired token wipe the list files together with the cached viewer and the profile file.
- **External links**: one `mediaDetail/domain/common/ExternalLink` model for media links (from the API) and person biography links, mapped to the UI by a single `ExternalLink.toLinkItem(strings)` (`detail` = language for media, `@handle` for people). Person links are enriched against the AniList site catalog (`ExternalLinkSourceCollection`, `ExternalLinkCatalogRepository` in `mediaDetail`, memory + 7-day disk cache) matched by normalized host (www/mobile/m, twitter↔x, youtu.be↔youtube.com) **including subdomains on a dot boundary** (`usuario.fanbox.cc` → `fanbox.cc`, never `notfanbox.cc`) with the most specific host winning; no match/offline falls back to a host-derived label with no icon. The catalog is `prefetch()`ed in the app's own scope at the start of a staff/character detail, overlapping the detail query and awaited only when the biography actually carries links; one shared in-flight request (Mutex-guarded creation) means never two at once, and a failed fetch is remembered for 10 minutes. The `mediaDetail/domain/common` extractor pulls anchors **and** bare URLs (with/without a "Label:") out of the biography, keeps real prose, and cleans leftover rótulos/separators.
- **Rail badges**: `ui/components/CoverStatBadge` (translucent icon+value pill) is shared by the studio grid and the dashboard rails; the caller owns the corner and skips nulls, and the values come from `ui/components/CoverStats` (`scoreBadge`/`popularityBadge`/`favouritesBadge`, one format everywhere). Dashboard cards show up to two badges chosen per rail in one place, `DashboardSectionKind.cardStats()` (`POPULAR_*` lead with popularity, `BEST_*`/season/trending/new-releases lead with the score), from the `averageScore`/`popularity`/`favourites` the rail query carries. Popularity/favourites render with `AppIcons.Groups`/`AppIcons.Favorite` + `core/model`'s `compactCount()` (`950`/`1.8K`/`12K`/`1.3M`), the score as `85%`.
- **Scroll rule (validated oct-2026)**: changing **what** is shown — a section chip, a filter, a sort, the calendar day, the Anime/Manga selector, a new detail destination — returns to the top; refreshing, closing a sheet or coming back (back, another tab) keeps the position. `ui/components/ScrollMemory` implements it: `rememberResetListState`/`rememberResetGridState` are `rememberSaveable` states keyed by their reset key, so a change re-creates the state **in the same composition** (the top is painted in the next frame, no effect tick) while a restore keeps the position. Survival across surfaces is Root's: the content area is wrapped in a `rememberSaveableStateHolder()` keyed by `"<slot tab>:<view>"` (`tab`, `settings`, `detail:<entryId>`, overlays) with `key(surface)` inside, so every tab, every detail-stack entry (identity per push, from `State.detailEntryIds`) and every overlay keeps its own saveable scroll state. A detail key carries the **composing slot's tab** (`detailSurfaceKey`) because a tab transition composes two slots and equal keys would crash, so a popped entry is dropped under every tab variant (`detailSurfaceKeys`). The provider must live inside `AnimatedContent`'s content lambda, and only the if/else chain is wrapped: the modals (sign-in, entry editor, share) stay outside it so their `remember`ed holders survive.
- **Debug timing**: debug builds log each GraphQL operation's duration (`MichiDependencies.isDebug` → Ktor client; Android reads `FLAG_DEBUGGABLE`, iOS `Platform.isDebugBinary`).
- **Load states**: `ui/components/LoadStateContainer` (spinner / retry error / empty / pull-to-refresh content, plus an optional compact non-blocking refresh error) is shared by the detail screens and the dashboard; loading/error labels arrive as parameters so it stays feature-agnostic (the detail screens pass no refresh error). The spinner block is `ui/components/LoadingPanel` (also used by the list/calendar screens); the `empty` slot paints when a load finished with nothing and no error (the dashboard's "no rails" panel). The genre/catalog pages gate it on the holder's `pageLoaded` flag (it has no detail model to test for null).
- **Detail poster grid**: `ui/components/DetailPosterGrid` is the one poster grid of a detail page (studio works, genre works, the "View all" people grids): token-sized `PosterCard` cells over the shared `MediaRailItem` (`ui/components`), a full-span `header` slot each screen fills with its own items (studio: hero + "Works"; genre: only the Anime/Manga switch — its name lives in the toolbar, so no title item and no "Works" line), an optional empty row (`emptyLabel` null = none), an optional per-item `cardOverlay` (the favourites grid's edit-mode remove button; when set the card does not navigate) and the auto-pagination footer. Studio/genre map their `MediaGridItem` with `MediaGridItem.toPosterItem()` (2 genres as subtitle, score + favourites badges, palette placeholder); a "View all" catalog maps through `MediaGridItem.toCatalogPosterItem(kind)` so its badges follow the rail's `cardStats()`. A genre's catalog switch re-queries page 1 and clears the works; the 18+ gate matches Discover's (hidden pins `isAdult: false`, allowed omits it) and flipping the setting re-queries page 1 without leaving the page.
- **Canonical genre link**: a genre is not an AniList entity, so its "open in AniList"/share URL is the catalog search filtered by genre (`…/search/{anime|manga}?genres=…`), percent-encoded through `discover/domain/genre/model/urlEncodeQueryValue()` (Ktor's `encodeURLParameter`, so non-ASCII goes through UTF-8) and following the Anime/Manga chip the user has selected.
- **Information grid**: `mediaDetail/ui/components/MediaDetailInfoGrid` is the one panel grid (label above uppercase value; short entries two per row with an odd tail kept half width, `wideEntries` full width) used by media, character, staff and studio. Panels wrap it in `MediaDetailPanel` + `SectionHeader`.
- **Spoilers**: `mediaDetail/domain/common/HtmlSpoilers` turns AniList's `markdown_spoiler` wrappers into private-use markers *before* cleaning, then returns the clean text plus inclusive `IntRange`s (`HtmlContent.spoilers`, `descriptionSpoilers` on the detail models). The rule is shared by biographies and the synopsis (`toSpoilerText()`), nested wrappers collapse to the outer range, an unclosed one runs to the end, stray closers are ignored and empty ranges are dropped; a stat inside a spoiler stays prose and its external links are still extracted. `SpoilerText.toSegments()` then splits the result: a range is a `Block` when it starts at the text start or right after a newline and ends at the text end or right before a newline, otherwise it stays inline inside a `Prose`; both keep the original range index, and prose strips leftover boundary newlines. The UI never paints hidden spoiler text. Inline ranges become `mediaDetailSpoilerHidden` (primary on `surfaceVariant`) as a `LinkAnnotation.Clickable` that reveals only that range. Blocks use `SpoilerBlock`: a flat content panel (`surface` + `flatBorder` + `PanelShape`, never glass) with a >=48dp header (`Role.Button`, action as `onClickLabel`) showing `AppIcons.Visibility`/`VisibilityOff` plus "Mostrar/Ocultar spoiler"; the block text is only composed when open, under a 1dp `outlineVariant` divider. Inline spoilers only reveal; blocks toggle. Collapsed shows the segments through the first `Prose` inclusive — blocks before it stay visible, closed and toggleable — with that prose at `COLLAPSED_LINES`; "read more" appears if it overflows or segments remain, and expanded shows all. Opening/closing a block never expands or collapses the section (body and container are not clickable; expansion stays on the read more/less row). Reveal state is a per-screen `SpoilerRevealState` keyed by detail id + text (a changed biography starts hidden), memory-only and lost with the detail. Tags: the section paints whenever `tags.hasTags()`; spoiler tags come after the regular ones as the same `FlatChip` with `ChipEmphasis.ALERT` (theme `error` text) and stay behind a `RailHeader` `TrailingPill` ("Spoilers (N)" ↔ "Ocultar spoilers"), hidden by default and memory-only.
- **Detail cache**: the four detail holders share `core/util/DetailCache` (pure, insertion-order eviction approximating LRU, plus `update(key, transform)`). A toggle-favourite response updates **its own** cached snapshot through `update` and only touches the visible state while the holder still shows that id, so opening another destination mid-request never mixes snapshots.
- **Rail paging**: every query that feeds a rail pages at a single `RailPageSize` (10, `core/model`) — the same value is the `perPage` and the rail's item count, and "View all" starts at page 1 and pages with it (characters/staff/recommendations, character/staff media, dashboard sections). Full grids page at `GridPageSize` (30) instead: the studio media grid and the genre works grid use it for their queries and fill themselves with the auto-pagination footer. `Media.relations` accepts no pagination args in the AniList schema, so the media detail trims its relation node to exactly what the rail renders (id/format/status/season/seasonYear/startDate.year/title/cover).
- **Sort sheet**: `ui/components/SortSheet` is the one sort picker (criterion group + order group, primitives in/callbacks out). The anime/manga lists map it to their holder (local sort); the studio grid maps it to `StudioDetailStateHolder`, and the genre/catalog grids to `CatalogGridStateHolder`, whose `changeSort` re-queries page 1 with the derived AniList `MediaSort` (server order, no client sort). `UserListSort.toMediaSort(order, isAnime)` (`core/medialist/domain`) is the single place that derives the API key; `DetailGridSortOptions` (`ui/components`) is the criteria list the studio/genre grids offer, and `CatalogSortOptions` adds `TRENDING` for the catalog sheets.
- **Auto-pagination footer**: `ui/components/LoadMoreFooter` + `LoadMoreKey` are shared by every auto-paging list/grid ("View all", the studio/genre grids). The last item is the footer; `ui/components/LoadMoreEffect` (one overload per lazy state kind) owns the `snapshotFlow` on the visible items, keyed by the loaded page, so a page that dedupes to nothing still re-triggers while a failed one does not (`distinctUntilChanged` + no page advance).
- **Font scale cap**: dense cards (`MediaCoverCard` rows and `PosterCard` cards, via `ui/components/CardDensity`) cap the OS font scale at 1.3× so content degrades to ellipsis instead of clipping and cover badges never collide; rail titles reserve two lines so the row stays even. Full-scale text lives on the detail screens (unbounded layouts). Validate at 200% OS font size.
- **Card pill priority**: in card bodies the action pills are measured first and pinned to the cover bottom (placed with `Arrangement.SpaceBetween`, like the lists); text slots are weighted (`weight(1f, fill = false)`) so overflow drops the last tertiary line (behind, `maxLines = 2`) instead of pushing the pills out.
- Reading: separate `+1 CH` and `+1 VO` buttons (manga has chapters and volumes). Animation: `+1 EP`.
- **Completing `+1`**: when a `+1` lands on the total (episodes/chapters/volumes), the card opens the entry editor pre-set to Completed (`State.openEditorForCompletion`) instead of saving from the list; the editor's Save is the only write, so cancelling leaves the entry at total − 1. The editor keeps **two baselines**: `saveBaseline` (the stored entry, before the prefill) drives Save, so it is enabled from the start of the completion flow, while `discardBaseline` (what the user sees on open, after the prefill) drives the discard prompt — a pristine completion sheet closes straight out without asking (the prefill is the app's edit, not the user's).

- Account stats: compact count label (e.g. `1.8K`) via the shared `core/model`'s `Int.compactCount()`.

## AniList / API Direction

- AniList uses GraphQL. Prefer typed/structured handling over ad hoc string concatenation.
- AniList api is limited to 30 request per minute
- The API serves adult entries to clients; filtering via `isAdult` is the client's job (`docs.anilist.co/guide/considerations`). Omit the var when 18+ is allowed (null = both) — never send `isAdult: true` (that filters to adult ONLY).
- Keep query/mutation definitions close to the repository/API surface that owns them.
- Keep AniList API concerns out of UI state and screens.
- Auth/session belongs behind `core.auth` or `core.session` abstractions (to be added).
- API DTOs must not leak into presentation state — map at feature/core boundaries.
- Model network errors, GraphQL errors, rate limits, and empty states explicitly for consistent UI rendering.
- Android system back uses `androidx.activity.compose.BackHandler`. iOS system back is no-op until native behavior is needed.
- Android deep links: the manifest registers `https://anilist.co|www.anilist.co/{anime|manga|character|staff|studio}/*` plus a `text/plain` `ACTION_SEND` share target (and the `michi://oauth/callback` filter). `MainActivity` routes OAuth vs links; `parseAniListDestination` returns a `DetailDestination` (Media/Character/Staff/Studio) from a URL or free text, it flows through `MichiDependencies.pendingDeepLink`, and `Root` calls `state.openDeepLink(destination)` before consuming it. `openDeepLink` closes Settings and pushes with the same no-duplicate-on-top rule as `openMedia` (which now delegates to it); the UI-only `openCharacter`/`openStaff`/`openStudio` are untouched. The web link is not verifiable (we don't own anilist.co), so Android sends it to the browser; **sharing** the link (Share → Michi) is the reliable path. iOS universal links are parked for the same reason.
